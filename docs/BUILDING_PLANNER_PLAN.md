# План развития: планирование внутри строений

## 1. Цель и пользовательский результат

Пользователь выбирает строение на плане участка, задаёт его назначение и этажность, переходит в редактор здания и проектирует каждый этаж отдельно. На плане этажа он добавляет комнаты, внутренние стены, двери, окна и специализированное оборудование из каталога либо создаёт собственный элемент. Изменения сохраняются в метрических координатах и сразу отражаются в 3D-модели здания на плане участка.

Критерии готовности пользовательского сценария:

1. Строение можно превратить в дом, гараж, баню, хозблок или пользовательский тип.
2. Можно задать 1–5 этажей, название и высоту каждого этажа.
3. У каждого этажа есть отдельный 2D-план с локальной системой координат от левого нижнего угла здания.
4. Элементы добавляются из понятного каталога, размещаются кликом и перемещаются мышью или touch с привязкой к сетке.
5. Двери и окна привязываются к наружным или внутренним стенам; MVP хранит положение и поворот, следующая итерация добавляет автоматическое snapping к сегменту стены.
6. Пользовательские элементы создаются без изменения backend enum: тип `custom`, название и произвольные properties.
7. 3D показывает этажность, окна, двери и различный внешний вид дома, гаража и бани.
8. Сервер остаётся источником истины: интерфейс показывает preview во время drag, сохраняет после drop и откатывается при ошибке.

## 2. Доменная модель и координаты

### Building

Расширение только для `plot_object.type = building`:

- `kind`: `house | garage | bathhouse | outbuilding | custom`;
- `roofType`: `gable | hip | flat | shed`;
- `wallMaterial`: `wood | brick | block | siding | custom`;
- `floorCount` выводится из этажей и отдельно не хранится;
- `properties`: расширяемые настройки внешнего вида без роста enum.

### Floor

- `id`, `buildingId`, `level`, `name`, `height`;
- level начинается с 1, уникален внутри здания;
- ширина и длина наследуются от footprint строения;
- координаты элементов локальные: `x ∈ [0, building.width]`, `y ∈ [0, building.length]`;
- высота пола вычисляется суммой высот предыдущих этажей.

### FloorElement

- `catalogKey`: стабильный ключ стандартного элемента либо `custom`;
- `category`: `room | wall | opening | furniture | equipment | utility | custom`;
- `name`, `x`, `y`, `width`, `length`, `height`, `rotation`;
- `geometry`: `footprint | polyline | polygon` и `points` для стен/комнат нестандартной формы;
- `properties`: JSONB только для параметров конкретного элемента, редактируемых типизированными UI-полями.

Стандартный каталог на первом этапе:

| Для всех зданий | Дом | Гараж | Баня |
| --- | --- | --- | --- |
| Комната, стена, дверь, окно, лестница | Кухня, санузел, кровать, шкаф | Ворота, машиноместо, верстак, стеллаж | Парная, печь, полок, душевая, слив |

Каталог определяется на frontend как типизированная конфигурация. Backend валидирует общую геометрию, но не закрепляет список `catalogKey`, поэтому новые элементы не требуют миграций.

## 3. API и хранение

Новые таблицы:

- `buildings`: один-к-одному с `plot_objects`, каскадное удаление;
- `building_floors`: уникальный `(building_id, level)`;
- `floor_elements`: принадлежит этажу, метрические поля и JSONB `points/properties`.

Маршруты:

- `GET|PUT /api/v1/plots/{plotId}/objects/{objectId}/building` — конфигурация здания вместе с этажами и элементами;
- `POST /.../building/floors`, `PATCH|DELETE /.../building/floors/{floorId}`;
- `POST /.../building/floors/{floorId}/elements`;
- `PATCH|DELETE /.../building/floors/{floorId}/elements/{elementId}`.

Все операции проверяют владельца через цепочку `floor → building → plot_object → plot`. Создание building-конфигурации идемпотентно через PUT. При увеличении этажности UI создаёт недостающие этажи; уменьшение требует подтверждения, поскольку удаляет планы верхних этажей.

## 4. Пользовательский интерфейс

### Точка входа

- При выборе строения карточка показывает назначение, этажность и кнопку «Открыть план здания».
- Отдельный маршрут `/plots/{plotId}/buildings/{buildingId}` сохраняет контекст участка и даёт больше места редактору.
- Первый вход предлагает короткий мастер: назначение → количество этажей → высота этажа → создать планы.

### Редактор этажей

- Верхняя строка: хлебные крошки, название здания, переключатель этажей, кнопка 2D/3D.
- Левая/нижняя панель на мобильном: каталог с поиском и фильтрами по назначению здания.
- Центр: масштабируемый SVG-план текущего этажа.
- Правая панель: свойства выбранного элемента; на 360 px открывается как нижняя панель.
- Добавление: выбрать элемент в каталоге, затем нажать место на плане; после размещения элемент остаётся выбранным.
- Перемещение: Pointer Events + pointer capture, preview, snap к сетке, координаты рядом с курсором, сохранение после drop.
- Точный ввод остаётся доступен через поля X/Y/размер/поворот.
- Touch targets не меньше 44 px; удаление всегда с подтверждением.

### Ошибки и пустые состояния

- Пустой этаж показывает три действия: «Добавить комнату», «Нарисовать стены», «Разместить дверь или окно».
- Ошибки полей приходят в React Hook Form через `setError`.
- Ошибка drag возвращает элемент в серверную позицию и показывает StatusMessage.
- Удаление этажа с элементами требует отдельного подтверждения с количеством элементов.

## 5. 3D-представление

- Высота здания равна сумме этажей плюс крыша.
- Материал и цвет фасада зависят от `wallMaterial`; форма крыши — от `roofType`.
- Окна и двери отображаются на фасадах по координатам элементов категории `opening`.
- Для гаража отображаются широкие ворота и более низкая/плоская конфигурация по умолчанию.
- Для бани — деревянный материал и дымоход при наличии печи.
- Сначала используется процедурная геометрия Three.js без загрузки внешних моделей; это быстро, предсказуемо и работает с любыми размерами.
- 2D остаётся обязательным fallback при отсутствии WebGL.

## 6. Этапы реализации

### Этап A — вертикальный MVP

- Миграции, доменные структуры, repository/service/HTTP CRUD.
- Конфигурация здания и управление этажами.
- Каталог минимум: комната, стена, дверь, окно и специализированные элементы garage/bathhouse.
- Страница здания, выбор этажа, создание и точное редактирование элементов.
- 3D-этажность, фасад, базовая крыша, окна и двери.

Статус: реализован первый рабочий срез — схема данных и CRUD API, мастер здания, этажи, контекстный каталог, 2D-план, drag со snap 0,5 м, точный инспектор и процедурный внешний 3D. Следующее усиление этапа A: управление существующими этажами и визуализация реальных проёмов из планов этажей на фасадах.

### Этап B — прямое манипулирование

- Drag элементов и вершин стен/комнат.
- Добавление кликом на canvas, snapping к сетке и стенам.
- Поворот ручкой, привязка дверей/окон к ближайшей стене.
- Undo/redo локальных действий до сохранения.

Статус: базовый drag прямоугольных элементов с pointer capture, preview, clamp, snap и сохранением после drop реализован; рисование стен по точкам, snapping проёмов и rotation-handle остаются следующими задачами.

### Этап C — качество проектирования

- Расчёт площадей помещений, длины стен и предупреждения о коллизиях.
- Межэтажные лестницы и проёмы.
- Размерные линии, печать/PDF и экспорт.
- Шаблоны этажей и копирование плана между этажами.

## 7. Тестирование и приёмка

- Domain tests: только building-объект получает конфигурацию; этажи уникальны; размеры конечны и лежат в footprint.
- Repository/API tests: изоляция владельцев, каскадное удаление, CRUD этажей/элементов, типизированные ошибки.
- Frontend schema tests: каталог, преобразование чисел, bounds, signed elevations и rotation.
- Component tests: мастер создания, смена этажей, добавление двери/окна, серверные ошибки, подтверждение удаления.
- Geometry tests: screen↔meters, snap, clamp, rotation, положение проёмов на фасаде.
- 3D smoke tests: этажность и building kind изменяют процедурную модель без падения 2D fallback.
- Mobile acceptance: полный основной сценарий на ширине 360 px и touch drag.

## 8. Совместимость и выпуск

- Миграции только добавляют таблицы и обратно совместимы со старым образом.
- Старые строения без `buildings` продолжают отображаться прежним box-renderer и получают конфигурацию только при открытии редактора.
- Новые API не меняют существующие payload участка и объектов.
- Feature выпускается поэтапно: сначала CRUD/точные формы, затем canvas interactions, затем расширенный 3D.
- Перед merge обязательны `go test ./...`, frontend lint/test/typecheck/build и проверка миграций на пустой и существующей БД.
